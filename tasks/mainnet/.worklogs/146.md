# Task 146 worklog

## 2026-08-21T21:50:00Z — root cause one: charge style frozen at deployment epoch

Built the offline reproducer first: `xtask cost-both-tx` re-runs one sealed
transaction against its parent trie (the MARF keeps every ancestor) with the
consensus cost tracker through both engines; `xtask cost-both` does the same
for a hand-written call, and `xtask cost-both-batch` audits thousands of calls
over one state open. On a reflink scratch of the witness state, the sealed
receipt reproduced exactly (compiler = the inflated 165496/30/77622/4/901,
interpreter = the canonical 161448/30/76653/4/341), so the whole differential
sits between clar2wasm's generated charging and the reference, offline, in
seconds.

A charge-stream trace (temporary `NANO_TRACE_COSTS` instrumentation in a
patched clarity worktree, never committed) plus decomposition through the
callee graph localized two generator defects:

1. **Charge style keyed to the wrong epoch.** Fourteen sites in
   `words/{maps,data_vars,equal,index_of,tuples}.rs` picked the pre/post-2.05
   charging rule from `contract_analysis.epoch` — the deployment epoch — so a
   contract deployed before 2.05 (marketplace-v4 is from 2021) kept charging
   2.0's *static type sizes* for map and variable operations forever, while
   the interpreter picks the rule from the runtime epoch and charges
   serialized bytes. Static tuple-of-principal sizes dwarf serialized ones
   (the on-sale fetch charged 683 against the canonical 246), which is the
   +969 read_length / +560 write_length / most of the +4048 runtime. Five
   more inverted (`< Epoch2_05`) sites in the same files plus `hashing.rs`
   double-charged once the first fix landed. All nineteen now go through
   `WasmGenerator::charges_serialized_sizes()`, which delegates to
   `executing_epoch()` — the cost epoch `compile_for_cost_epoch` already
   plumbs — exactly like the `uses_arg_size_for_cost` sites the earlier cost
   work fixed in `tokens.rs`.

2. **Trait references sized as their type, and paying a copy they never
   make.** A trait argument's charge size is its *value*: a bare contract
   principal (148) in a Clarity 1 contract, a callable carrying its trait
   identifier (276) from Clarity 2 on. `runtime_size`'s catch-all charged the
   *type* size (276) regardless, and `visit_atom` charged
   `LookupVariableSize` on trait reads that the reference hands back owned
   from the callable context (Clarity 1 only) without any copy charge.
   Both are now version-exact (`is_trait_reference` /
   `reads_owned_callable`).

With both fixes the block-8,808,752 transaction charges **exactly the
canonical record on all five dimensions**, and the minimal shapes are pinned
as `recorded_semantics_charges` crosscheck-cost tests in `words/maps.rs`,
using `crosscheck_cost_recorded_semantics` (deploy under Epoch20/Clarity1,
charge at the current epoch) — the harness combination none of the existing
cost tests exercised, which is why the suite was green over a 30% mainnet
differential.

## 2026-08-22T05:40:00Z — the three-dimension family is closed; the residual is runtime-only

The sweep finished: 1,736 of the hold window's 6,243 blocks (27.8%) carried at
least one cost mismatch against the canonical record. Re-running every
transaction of every one of those blocks through both engines with the fix
(`cost-both-batch`, 3,659 contract calls, no errors) leaves **1,611
disagreements, 1,609 of them runtime-only** — every read_length and
write_length difference is gone, on every call in the window, and both
count-bearing dimensions agree everywhere except two transactions.

So the family the differential opened with is closed. What remains is a
narrower one: runtime deltas clustered on a few repeated magnitudes (+62 on
438 calls, +33 on 312, +8 on 187, +1281/+1289 on 57, −276 on 15, and a long
tail), plus exactly two calls where nano performs one extra charged read and
write — `BNS-V2::name-claim-fast` (18/7 against the canonical 17/6, runtime
−3761, lengths and root identical), which is an operational difference rather
than a pricing one and needs its own reduction.

Localizing runtime deltas needed a new instrument. Wasm charges accumulate in
module globals and reach the tracker only at sparse flush points, so a
several-dozen-unit difference inside a million-unit transaction was smeared
across hundreds of charges. `NANO_TRACE_CHARGES` (committed) makes every
generated charge report its word label and scaling input, so the two engines'
charge streams can be aligned event by event. The first case it resolved is
the +33 family: on a `(is-eq (some burn-hash) (get-burn-header burn-height))`
the compiled engine charges one `LookupVariableSize` on a 16-byte argument
that the reference never charges — the reference's cost for reading a binding
depends on whether its consumer materializes the value or borrows it, which
the compiler currently does not model.

Two notes for whoever picks this up. The compiler identity hashes the whole
vendored tree, so *any* edit there — including a comment — moves the profile
fingerprint and invalidates a state's recorded profile; the published
checkpoint sample is repinned in the same commit as each compiler change, and
diagnostic runs belong on a reflinked scratch state. And the fixes so far
already supersede the frozen release artifact 16e0928a: its compiler is the
one with the inflated charges, so the 24-hour hold evidence gathered on it
describes an artifact that will not be the release candidate.

## 2026-08-22T12:20:00Z — second census: the +33 family closed, +62 and +8 remain

Re-ran every transaction of every mismatched hold block against the fixed
compiler: **3,658 calls compared, 1,313 disagree, down from 1,611**, and still
zero length-dimension differences anywhere. The drop is exactly the family the
borrow fix closed: `+33` fell from 312 calls to 15.

What remains, in order: `+62` on 438 calls, `+8` on 187, `+1281`/`+1289` on 57,
then a tail including negatives (`-276`, `-184`, `-92`), plus the same two
calls with an extra charged read and write (`BNS-V2::name-claim-fast`).

Three things worth knowing before picking this up.

The `+62` family is one shape and one deployer: tiny router contracts
(`SP2H674PRTZV6YW56K0FMR7GDGZE4ZC5HMYZ3CDEV.psis` and its siblings `gent`,
`phis`, `daud`, `tuna`) that forward a `(buff 400)` parameter through a trait
dispatch into `SP2H674PRTZV6YW56K0FMR7GDGZE4ZC5HMYZ3CDEV.swag`, a 32 KB
contract of trait-typed list entry points. Reducing the router alone does *not*
reproduce it — a probe of exactly that shape charges identically — so the
divergence is inside `swag`, and the next step is bisecting `swag`'s entry
points rather than the router.

Charge-stream diffing does not work on this contract, and it is worth saying
why so nobody repeats it: over the psis transaction the compiled engine makes
about 1.5x as many charge events as the reference (17,144 `get` against 11,860,
4,120 `if` against 2,683) while the two totals agree to within 62 units. The
engines decompose the same work into different numbers of events, so event
counts and per-word input multisets are both noise here; only aligned small
streams are informative, which is how `+33` was found.

`+62` cannot be a single `LookupVariableSize` — that charge is `2n+1`, always
odd — so unlike `+33` it is at least two charges or a different cost function,
which is consistent with it living deeper in a call chain.

Also recorded: the sample repin trap. The compiler identity hashes the vendored
tree *as it is on disk*, so measuring the active fingerprint in a working tree
that carries another session's uncommitted clar2wasm edit pins a value that was
never committed. That happened here and the gate caught it in a clean checkout;
the fix is to regenerate the sample in a clean worktree, which 2011cdeb does.

## 2026-08-22T14:10:00Z — the runtime residual cannot be adjudicated by the interpreter

Localizing `+62` exactly is what exposed the framing error in everything above,
so this entry is a correction as much as a result.

`+62` was localized precisely. Calling `swag.ss` on real mainnet state charges
identically to the interpreter for one and two list elements and diverges by
exactly 62 from three on; per element, `swag.sr` is exact on the slices that
dispatch to `token-stx-v-1-2` and diverges by 62 on the two that dispatch to
`token-stx-v-1-1`, which are also the ones whose execution aborts. Both token
contracts have identical `transfer` signatures, both declare the same
(different) trait, and calling either directly is exact — so the divergence
needs the dynamic dispatch *and* the failing callee together. Reduced probes of
each ingredient separately (fold over a trait list, a failing dispatch, an
arithmetic underflow, a router forwarding a buffer) all charge identically, so
the reduction is not finished.

Then the check that matters. For that transaction nano's **sealed** cost was
`runtime 57,123,371` against a canonical `57,123,733` — nano was **362 below
the real chain**, while the compiler is 62 *above* the interpreter, which puts
the interpreter roughly 424 below canonical here. **The interpreter is the
outlier on this shape, not the compiler.** Every "disagreement" counted in the
two censuses above is compiler-versus-interpreter, so those 1,313 numbers do
not say that nano disagrees with the chain; on this shape the engine they
measure against is the one further from it.

What is actually established, and against the authoritative oracle:

- Block 8,808,752 carries exactly one transaction, so its block cost *is* that
  transaction's cost and an exact canonical comparison is possible. With the
  fixed compiler it matches the canonical record on all five dimensions. That is
  the differential this task opened on, closed against the chain rather than
  against the interpreter.
- The three charging fixes were verified against the reference's own source —
  `eval` then `as_ref`, never `clone_with_cost` — not merely against the
  interpreter's behaviour.
- Every `read_length` and `write_length` difference in the window is gone.

What remains, restated honestly: the runtime dimension. Nano's sealed runtime
differs from canonical in *both* directions across the window (`-362` here,
positives elsewhere), and neither the interpreter comparison nor a single-block
canonical check can settle it at scale. Settling it needs the hold window's
blocks re-executed with the fixed compiler and their receipts compared to the
canonical record — which is this task's last subtask and exactly what unblocks
106. `cost-both-tx` cannot substitute: it runs one call against a parent without
the block's transaction prefix, so its numbers are not comparable to a sealed
receipt.

The instrument for that work now exists and is worth keeping: the charge probe
reports the runtime meter after every charge (index `-1`), so a compiled charge
stream can be compared to the reference's cost for cost rather than by event
name. That is what showed the local sequence differences around `len` and
`mod` to be ordering, not pricing.

## 2026-08-22T15:30:00Z — the canonical audit needs a re-attested checkpoint first

Tried to stand up the canonical-oracle measurement the entry above asks for: the
fixed node following mainnet, every executed block's receipts compared against
the chain's own record. It does not start, for a reason that is itself the
finding.

A node refuses to run against a checkpoint bundle whose recorded compiler
identity is not its own — `checkpoint profile 5561d364… does not match this
artifact's …` — and `[checkpoint]` is not optional even when the state is
already imported. The bundle binds the compiler that produced its state root,
and the builders signed that binding. So the cost fixes do not merely supersede
the frozen artifact 16e0928a as a *binary*; they invalidate the attested
checkpoint bundle that artifact imports, because the bundle names
`sha256:1f78d344` and profile `5561d364`.

That makes the ordering for closing this task explicit, and it is longer than
the remaining code work:

1. Finish the runtime dimension in the compiler (the `+62`, `+8` and `+1281`
   families, and the two extra-read/write calls).
2. Re-run the checkpoint builder ceremony for the new compiler identity so a
   bundle exists that a fixed node will accept — the task 134 tooling, with
   builder policy and signatures, not a hand-edited manifest. Rewriting the
   recorded identity in a copied bundle would forge exactly the binding the
   builders signed, so it is not an option.
3. Import that bundle fresh and re-execute the window, comparing every receipt
   to the canonical record. That is what closes this task and unblocks 106.

Two smaller notes from the attempt, both worth keeping. The release follower
artifact deliberately rejects `event_observer` and `rpc_bind` (task 135's
minimal-surface work), so receipt capture needs the full node binary — the
follower cannot be the audit subject. And a binary built in a working tree that
carries another session's uncommitted `clar2wasm` edit reports a different
profile fingerprint than the committed content does (`604cc589` against
`1d7b821a`); anything measuring compiler identity has to be built from a clean
checkout, which is the same trap the sample repin fell into earlier today.
