# Task 146 worklog

## 2026-08-21T21:50:00Z — root cause one: charge style frozen at deployment epoch

Built the offline reproducer first: `xtask cost-both-tx` re-runs one sealed
transaction against its parent trie (the MARF keeps every ancestor) with the
consensus cost tracker through both engines; `xtask cost-both` does the same
for a hand-written call, and `xtask cost-both-batch` audits thousands of calls
over one state open. On a reflink scratch of the witness state, the sealed
receipt reproduced exactly (compiler = the inflated 165496/30/77622/4/901,
interpreter = the canonical 161448/30/76653/4/341), so the whole differential
sits between clar2wasm's generated charging and the reference, offline, in
seconds.

A charge-stream trace (temporary `NANO_TRACE_COSTS` instrumentation in a
patched clarity worktree, never committed) plus decomposition through the
callee graph localized two generator defects:

1. **Charge style keyed to the wrong epoch.** Fourteen sites in
   `words/{maps,data_vars,equal,index_of,tuples}.rs` picked the pre/post-2.05
   charging rule from `contract_analysis.epoch` — the deployment epoch — so a
   contract deployed before 2.05 (marketplace-v4 is from 2021) kept charging
   2.0's *static type sizes* for map and variable operations forever, while
   the interpreter picks the rule from the runtime epoch and charges
   serialized bytes. Static tuple-of-principal sizes dwarf serialized ones
   (the on-sale fetch charged 683 against the canonical 246), which is the
   +969 read_length / +560 write_length / most of the +4048 runtime. Five
   more inverted (`< Epoch2_05`) sites in the same files plus `hashing.rs`
   double-charged once the first fix landed. All nineteen now go through
   `WasmGenerator::charges_serialized_sizes()`, which delegates to
   `executing_epoch()` — the cost epoch `compile_for_cost_epoch` already
   plumbs — exactly like the `uses_arg_size_for_cost` sites the earlier cost
   work fixed in `tokens.rs`.

2. **Trait references sized as their type, and paying a copy they never
   make.** A trait argument's charge size is its *value*: a bare contract
   principal (148) in a Clarity 1 contract, a callable carrying its trait
   identifier (276) from Clarity 2 on. `runtime_size`'s catch-all charged the
   *type* size (276) regardless, and `visit_atom` charged
   `LookupVariableSize` on trait reads that the reference hands back owned
   from the callable context (Clarity 1 only) without any copy charge.
   Both are now version-exact (`is_trait_reference` /
   `reads_owned_callable`).

With both fixes the block-8,808,752 transaction charges **exactly the
canonical record on all five dimensions**, and the minimal shapes are pinned
as `recorded_semantics_charges` crosscheck-cost tests in `words/maps.rs`,
using `crosscheck_cost_recorded_semantics` (deploy under Epoch20/Clarity1,
charge at the current epoch) — the harness combination none of the existing
cost tests exercised, which is why the suite was green over a 30% mainnet
differential.

## 2026-08-22T15:30:00Z — the canonical audit needs a re-attested checkpoint first

`sha256:1f78d344` and profile `5561d364`.

the remaining code work:

   families, and the two extra-read/write calls).
2. Re-run the checkpoint builder ceremony for the new compiler identity so a

## 2026-08-23T02:30:00Z — a real fix from the canonical audit: 822 of 848

The index-0 observation is what unblocked this. A transaction at index 0 in its
block has no prefix, so `cost-both-tx` against the parent reproduces the chain's
exact path — 11 of the 55 differing transactions were at index 0, and one of
those (`0xf8985deb` at 8,813,012) was the only transaction in its block, making
its canonical comparison exact.

That transaction charged 402 runtime units too many, its compiler-versus-
interpreter delta was also exactly 402 (so the interpreter is the oracle on this
path), and the before/after meter probe localized it cleanly: 150 `concat`
charges, **equal counts on both engines**, compiler total 5,052 against the
reference's 4,650. Pairwise, the compiler passed n=4,400 where the reference
passed 275 — exactly sixteen times, the in-memory width of a `uint`.

**`concat` was charged for the bytes its memory copies moved, not for the items
it joined.** The reference's `special_concat` accumulates `seq.len()`, which is
items; nano accumulated the byte span it needed for `memory_copy` anyway. A
buffer or an ASCII string hides this completely — an item there *is* a byte —
which is why every existing `concat` crosscheck was green. Fixed by dividing by
the element stride for lists and by four for UTF-8 strings, with probes pinning
lists of `uint` and `int` and a UTF-8 string.

Re-running the same ten windows measures it: **822 of 848 transactions now match
the canonical record on all five dimensions, up from 793.** The fix closed 29 of
the 55, more than half, and windows 7 and 9 are now perfect. Residual: 26
transactions, 3.1%, still all runtime-only.

## 2026-08-23T04:15:00Z — the position probe, and the limit it exposes

Built the instrument the previous entry asked for: both engines now report
*where* each charge belongs, not just what it was. The compiler tracks the
`SymbolicExpression` it is traversing and emits an interned `contract#id`
before each charge; the reference prints the same pair at every `eval`. So a
charge stream can be grouped by source position instead of by label, which is
what a comparison needs when the two engines decompose the same work into
different numbers of events.

It immediately shows two things, one useful and one disqualifying.

The useful one: the engines attribute a charge to *different nodes* — the
compiler to the expression it is traversing, the reference to the innermost
`eval` — so positions come in offsetting pairs (`stableswap-core#868` at
+364,800 against `#1121` at −362,016 for the same work). Any positional
comparison has to normalize that, by parent or by contract.

The disqualifying one: **the extracted per-charge costs sum to more than the
transaction actually cost** — 6,669,529 against a real 6,515,639 — with no
negative deltas and no outlier (the largest single charge is a legitimate
13,400 `contract-of`). So the arithmetic is not corrupted; the meter is. The
host syncs the cost globals between caller and callee instances, and a caller's
charges that have not yet been flushed to the tracker when a callee's instance
is seeded get counted twice. Which means before/after meter differencing is
**exact within one instance and unreliable across a nested call**.

That retroactively explains which of this task's findings were safe. `pox-5`
(one contract) and `concat` (150 charges in one contract, compared per label
with equal counts) were both in the exact regime, and the `concat` fix verified
against the canonical record to the unit. The `+8` family spans six contracts,
so it is squarely in the unreliable regime, and the per-contract deltas it
produces (+185,033 on `stableswap-core-v-1-4`) are extraction artifacts rather
than findings — recorded explicitly so nobody chases them.

Closing the remaining 26 therefore needs the meter made exact across calls:
flushing the wasm globals to the tracker at every charge in a traced build, so
that no charge is ever counted in two places. That is a contained change to the
traced-build path and it is the next step, ahead of any further reduction
attempts.

## 2026-08-23T05:00:00Z — what the position data says, and where it stops

Two mechanisms in the extraction are now identified rather than suspected.

The inflation is `run_free`. A callee executed through `ExecutionState::run_free`
— `short_circuit_cost` in the `contract-call?` host function — still decrements
the callee module's cost globals, because generated code always does, while the
tracker is never charged. My probe measures the globals, so it counts work the
transaction did not pay for. In the `+8` transaction those regions are 583,502
units across 24 positions the reference never charges at all, which is most of
the 153,890 by which the extracted sum exceeded the real runtime.

What remains after excluding them is not yet a comparison. The two engines
attribute a charge to different nodes — the compiler to the expression it is
traversing, the reference to the innermost `eval` — so the same work appears as
offsetting pairs: `stableswap-core#1121` is 362,016 *low* on the compiler side
while its neighbours are correspondingly high, and the net over shared positions
is −84,667 rather than the +8 the transaction actually differs by. Positional
comparison needs the attribution normalized (fold each charge up to a common
ancestor, or compare subtree totals) before an 8-unit difference inside 6.5
million across six contracts can be read off it.

So the specified next step is now two things, not one: identify and exclude
`run_free` regions (the host knows when it enters one and can say so through the
same probe), and normalize attribution to subtree totals. Both are contained
changes to the traced path. Until they exist, this task's reliable findings come
from single-contract transactions and from per-label comparisons where the event
counts agree — which is how `concat` was found and fixed, and it is worth noting
that that one fix closed more than half the canonical residual.

## 2026-08-23T06:30:00Z — retracting the run_free diagnosis

The entry above blames the extraction's inflation on `run_free`: a
short-circuited callee decrementing the module's cost globals while the tracker
goes uncharged. I instrumented the boundary to confirm it — the
`contract-call?` host function now announces `free-enter`/`free-exit` when
`short_circuit_cost` is taken — and re-traced the `+8` transaction.

**Zero free regions.** The transaction never takes that path, so `run_free`
cannot explain anything about it. The diagnosis was wrong and is withdrawn; the
marker stays, because it costs nothing and the next person to suspect free
regions can rule them out in one run instead of an afternoon.

What is established about the extraction, stated as measurement rather than
mechanism:

- On a **single-instance** trace it is exact. `pox-5.stake-update`'s 48 charges
  sum to 30,278, its `cost_load_contract` is 137,147, and 30,278 + 137,147 is
  167,425 — the runtime to the unit.
- On a **multi-instance** trace it over-counts. The `+8` transaction extracts
  6,669,529 where the wasm-side total should be about 6,275,639 (6,515,639 less
  roughly 240,000 of host-side contract loading), so about 394,000 too much,
  spread across no outlier and with no negative delta anywhere.

Ruled out so far: free regions (measured, zero), arithmetic corruption (no
negative or oversized deltas; largest single charge is a legitimate 13,400
`contract-of`), and probe mis-pairing on branch boundaries (the four probe
emissions per charge all go into the same instruction sequence).

Still unexplained, and this is the blocker for the remaining 26: why summing
per-charge deltas across instances exceeds the transaction's wasm-side cost.
Until that is understood the multi-contract traces cannot be trusted, and the
landmark-aligned cumulative walk built on top of them drifts to −187,668
instead of converging on the +8 the transaction actually differs by. The next
step is to instrument the *instance boundary* itself — report the meter on both
sides of every seed and write-back — rather than to attempt another reduction.

## 2026-08-23T07:30:00Z — I instrumented dead code, twice

`link_contract_call_fn` at `linker.rs:6087` — the function whose
`short_circuit_cost`/`run_free` branch and whose `remaining_costs` /
`set_remaining_costs` hand-off both entries above reason about — carries
`#[cfg(any())]`. That is `cfg(false)`: permanently disabled. There is a second,
live `link_contract_call_fn` at `linker.rs:6323`, and it is the one registered
in `link_host_functions`.

So both markers I added measured nothing, and the "zero free regions" that made
me retract the `run_free` diagnosis was zero because the code cannot run, not
because free regions do not occur. The retraction stands — that diagnosis was
never demonstrated — but its stated evidence was worthless, which is worse than
having no evidence, and the markers are removed rather than left where they can
mislead again. The give-away was available and I missed it: `cost_meter`, the
field that branch assigns, does not exist anywhere in the clarity revision this
tree builds against.

What reading the *live* path does establish is the accounting model, and it is
not the one I assumed. A nested call runs in an instance whose cost globals
start at `i64::MAX`; at exit, `call_function_with_argument_sizes` computes
`CostMeter::used_from_remaining(remaining)` and returns that as the call's cost.
So instances do not share a meter and are not seeded from the caller —
each reports what it used, and the tracker sums them. Whether the same instance
can serve nested calls without its inner call being counted twice is the precise
question to answer next, because that is the only mechanism left that would make
per-charge deltas summed across instances exceed the transaction's wasm-side
cost, which is what the `+8` trace does by about 394,000.

The lesson worth keeping, and the reason this entry exists at all: before
trusting an instrument, check that the code it instruments runs. A marker that
never fires reads exactly like a measurement of zero.
